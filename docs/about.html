About

What is measured, what is known to be wrong, and how to work on it.

Limitations

Every one of these is a real edge the framework has, documented because a character grid fails visibly and an undocumented failure looks like a bug in your page.

chromium
The calibration is Chromium-only, and build-specific. Firefox and Safari round font metrics differently and have not been measured, and even within Chromium the measured limit moves with the build: re-sweeping an unchanged tree on the same reported version has come back 1px more permissive on a third of the rows, with no 16px row affected. The shipped ratios are the stricter measurement. The behavior layer is Chromium-tested only too — it uses <dialog>, :has() and round(), all supported in current Firefox and Safari, none covered by a spec run here.
seams
Faint horizontal seams at some font sizes. A glyph is painted at its natural em advance inside a cell rounded up to a whole pixel, and the difference stays unpainted. Sizes where the product is an integer — 15, 20 and 25px for JetBrains Mono and JuliaMono, even sizes for Iosevka — are clean for the line glyphs; █ keeps a ~0.09px loss even then. Avoid long runs of it. The skin's glow covers the seam, which is not the same as fixing it.
flex
Several .col children sharing leftover space can land on a fractional cell. Use .col-N where exactness matters.
wide glyphs
CJK and emoji occupy two cells and nothing accounts for it. Out of scope for v1.
tooltips
.tip on a plain <span> is hover-only until it gets a tabindex. The module does not add one: silently rewriting a page's tab order is worse than the gap.
tabs
A tab strip is horizontal only. Arrow keys are left and right; a vertical tablist is not written.
the glass
The scanlines are glass, not a texture. The overlay is fixed to the viewport, so the lines sit on the row grid at rest and after a scroll of a whole number of rows, and mid-row at any other offset. An overlay that scrolled with the content would be aligned always but would not cover a pinned status bar, a toast stack or a drawer.
the top layer
The skin does not cover an open <dialog>. A modal opened with showModal() is in the top layer, which paints above every z-index there is. The dim behind it is under the glass; the dialog itself is not. And a .crt on a box erases that box's border, because both want the same two pseudo-elements.
collapse
A collapse body is a formatting context, so a margin on its first or last child sits inside the body rather than collapsing through it. That is deliberate — the clamp used during the animation establishes one anyway, and a body that only did so while opening would measure one height and animate to another — but it spaces slightly differently from a plain <div>.

What is measured

Test-driven wherever it is measurable, which in a framework whose whole claim is geometric is nearly everywhere.

suitetestswhat it holds
themes.spec.js206theme contract and contrast
readme.spec.js8every claim the README can be held to
grid.spec.js46integer cells, continuous borders
default.spec.js5the default paints, a link beats it
behavior.spec.js180layer 4, cell-exact mid-animation
skin.spec.js27layer 3 moves nothing, inert unapplied
docs.spec.js339this site, page by page
metrics.spec.js340font metrics — 100 known failures

The 100 failures are a wrong assertion rather than a layout bug. metrics.spec.js asserts that 80 cells equal 80 × the font's em advance × the font size, taken from the font tables — but Chromium lays monospace text out with whole-pixel advances, so a cell is the rounded product: 10px at 16px JetBrains Mono, not 9.6px. The grid property that matters still holds — N cells is N equal whole-pixel columns, regular and bold, with no drift as N grows. The prediction the assertion checks is not the one the browser uses.

This site is in that table. Every page here is loaded twice — once normally and once with JavaScript disabled — and swept for integer cells, cell boundaries and continuous borders, which is the only reason to build the documentation out of the thing it documents.

Development

npm install
npm run serve          # http server + the test pages
npm test               # node:test; the browser specs need Playwright
npm run font-limits    # font tables       -> fonts/metrics.json
npm run calibrate      # line-height sweep -> test/calibration.json

Re-run both calibration steps after changing a font file or the Chromium version, then copy each ratio into tokens.css — the spec fails if they disagree.

npm run serve prints the URL of the test index, which links the kitchen-sink pages: every CSS component, the behavior layer with a motion switch, the skin with its tokens on live controls, the framework with no theme link at all, and the font calibration harness. Each is built with the framework it tests, as this site is.

PLAN.md is the design document: the rules, the layer architecture, the measured font metrics, and the reasoning behind each rejected alternative. It is the file to read before changing anything here.
